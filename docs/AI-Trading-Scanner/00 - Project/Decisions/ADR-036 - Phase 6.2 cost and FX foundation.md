# ADR-036 — Phase 6.2 cost and FX foundation

- Status: ACCEPTED as Phase 6.2 cost/FX policy. Implementation in this milestone is bounded to immutable evidence/profile contracts, their own validation, and (as of 2026-09-19) one pure, non-posting FX conversion *calculation* for `SELL_BASE_FOR_TRADING` only; balanced-leg capital posting, actual conversion execution, manifest V3 binding, fees/spread/slippage on a conversion, and the reverse conversion direction all remain pending separate authorization.
- Date: 2026-09-18.

## Context

The accepted Phase 6.1 order/terminal resolver has no fill, cost or FX authority. [[01 - Architecture/Execution/Replay and Simulation Architecture]] and [[04 - Costs & Economics/Transaction Costs]] already describe the target: an immutable, content-identified transaction-cost profile (`SIMULATED_IBKR_US_TIERED`, numeric values still unselected) and causal `FxObservation` evidence feeding a versioned conversion/valuation policy (tentatively `INITIAL_CONVERSION_AND_REPORTING_MARK_V1`), with the exact FX source, freshness threshold, quote convention and rounding explicitly left as open registration decisions. `TransactionCostConfiguration`, `FillCostBreakdown` and `calculate_fill_costs` already exist and are accepted; no FX contract exists yet. Milestone 6.2 must add the missing contracts without inventing the unset numeric values, without silently changing any accepted Phase 1–6 identity, and without granting execution or posting authority ahead of Milestones 6.3+.

## Decision

Introduce two new pure, content-identified modules, `ai_trading_scanner.simulation.costs` and `ai_trading_scanner.simulation.fx`, and keep FX conversion cost tracked separately from per-fill trading cost rather than extending the accepted `TransactionCostConfiguration`. That contract, `calculate_cost_model_id` and `calculate_fill_costs` are unmodified by this decision; their identity and behavior are unchanged.

`CostProfileRegistration` is a sourcing/audit envelope that references an existing `TransactionCostConfiguration` by its `cost_model_id` only — it never duplicates or carries the numeric fee schedule. Its `status` is `REQUIRES_SOURCING` or `SOURCED_AND_VALIDATED`; a sourced-and-validated registration must carry `source`, `source_reference`, `effective_date` and `validated_by`, and an unsourced one must omit them. `require_sourced_cost_profile` fails closed (`CostProfileNotSourcedError`) unless the registration is sourced, validated and references the exact supplied configuration. No run may use a cost profile that is not registered as sourced and validated; this milestone adds the enforced gate, not the sourced values themselves. `SIMULATED_IBKR_US_TIERED`'s real commission schedule remains unselected and is explicitly out of scope for this ADR.

`CostRoundingPolicy` formalizes the accepted V1/V2 rounding behavior (`ROUND_HALF_EVEN` at 34-digit Decimal precision, already used unversioned inside `calculate_fill_costs`) as an explicit, versioned, referenceable policy identity (`ROUND_HALF_EVEN_V1`). Adopting this enum changes no existing V1/V2 calculation, contract or content identity; it only gives the new cost/FX contracts introduced here an explicit rounding reference instead of an implicit one.

`FxObservationReference` is immutable causal FX evidence, modeled directly on the accepted `MarketEventReference` causal-availability shape: `available_at` must not precede `observed_at`, and the observation is not usable before `available_at` once a causal resolver exists. Its `rate` is supplied evidence from an external provider — never computed, defaulted or invented by this contract or any engine code. `FxQuoteConvention` (`BID`, `ASK`, `MID`, `DECLARED_REFERENCE`) makes the side/price convention an explicit, versioned field on both the observation and the policy; no convention is an implicit production default.

`FxConversionPolicyConfiguration` is an immutable, versioned policy (tentatively named `INITIAL_CONVERSION_AND_REPORTING_MARK_V1`, matching the architecture document) binding `base_currency`, `trading_currency`, `quote_convention`, `maximum_observation_staleness_seconds` and `rounding_policy`. None of these has an engine-supplied default, mirroring how `SimulationLiquidityConfiguration` carries no default participation ceiling; the actual staleness threshold, and any real FX source/methodology, remain open registration decisions pending owner sourcing, exactly like the unset cost profile.

**Rate direction (owner-approved, 2026-09-18):** `FxObservationReference.rate`, and any future policy-level rate under this design, is `quote_currency`/`trading_currency` units per 1 unit of `base_currency`. For the EUR-funded/USD-trading Experiment 1 profile, `rate = 1.10` means `1 EUR = 1.10 USD`. This is a general convention for the FX contract, applicable to any future registered currency pair — it is not a hard-coded EUR/USD-only rule, and Experiment 1's actual scope remains limited to its separately registered EUR-funded/USD-trading configuration. This resolves one specific open design question; it does not resolve the exact FX source, bid/ask/mid quote-side selection, the numeric staleness threshold, or rounding, all of which remain separately open. No conversion, valuation, quote-side selection, fee, balanced-leg, or manifest V3 code is implemented by this decision.

**Five remaining FX design decisions (owner-approved, 2026-09-18):**

1. *Source checksum:* `calculate_fx_source_checksum` hashes exactly six logical fields — `base_currency`, `quote_currency`, `provider`, `quote_convention`, `rate`, `observed_at` — via the existing V2 canonicalization and SHA-256 content-identity helpers (unchanged). Decimal representation is scale-invariant, consistent with every other Phase 6 V2 identity. The checksum represents the normalized provider fact, not the provider's original transport bytes.
2. *Decimal arithmetic:* future conversion/valuation arithmetic uses the project's existing 34-digit Decimal precision where applicable, with no intermediate monetary rounding; quantization happens once, at the final posting boundary, using `ROUND_HALF_EVEN_V1`. Currency minor-unit precision must be an explicit, configurable value when that posting logic is built — never universally hardcoded to 2. Not implemented by this ADR; `calculate_fill_costs`'s existing behavior is unchanged.
3. *Quote sides:* selling EUR to obtain USD requires a sourced EUR/USD `BID`; reporting-only valuation uses `MID` or an explicitly declared reference quote and is now structurally enforced — `FxValuationPolicyConfiguration` rejects `BID`/`ASK` outright. No side is ever silently substituted for another.
4. *Policy separation:* `FxConversionPolicyConfiguration` (existing, left completely unmodified — its own identity, tests and reviewed history are untouched) is the executable conversion policy; the new `FxValuationPolicyConfiguration` (its own `fx-valuation-policy-v1` schema version, its own `FxValuationPolicyId` identity domain) is reporting-only. Neither type carries a capital-movement or cost field; valuation never moving capital or incurring a cost is enforced by that absence, not by a runtime check, since no posting code exists anywhere in this module.
5. *Missing evidence:* `select_eligible_fx_observation_for_conversion` and `select_eligible_fx_observation_for_valuation` return typed `FxConversionQuoteUnavailable`/`FxValuationQuoteUnavailable` evidence — distinguishing "no causally eligible observation at all" (`NO_ELIGIBLE_OBSERVATION`) from "eligible observations exist but none match the required quote side" (`REQUIRED_QUOTE_SIDE_UNAVAILABLE`) — rather than fabricating or substituting a value. A conversion cannot proceed without its required quote; a valuation must be treated as explicitly incomplete reporting.

*Implementation note (2026-09-18):* at the time the five decisions above were recorded, `FxConversionPolicyConfiguration` was deliberately left completely unmodified rather than adding a BID/ASK-only structural constraint to it directly, because doing so would have broken its own already-committed, already-reviewed tests (which use `DECLARED_REFERENCE`/`MID` as its default `quote_convention`). The BID-for-conversion rule was recorded as a registration-time expectation only, not a type-level constraint.

**`fx-conversion-policy-v2` — required transactional quote side (owner-authorized, 2026-09-19):** closes that gap additively. `FxConversionPolicyConfiguration` gains an optional `schema_version` value `"fx-conversion-policy-v2"` and a new field `conversion_direction: FxConversionDirection | None`, forbidden for V1 and required for V2. `FxConversionDirection` currently has exactly one member, `SELL_BASE_FOR_TRADING` (e.g. sell EUR, receive USD) — the only direction the owner has approved a quote-side rule for; a `V2` policy with that direction must declare `quote_convention = BID`, structurally enforced, and any other side (`MID`, `ASK`, `DECLARED_REFERENCE`) is rejected at construction. The reverse direction (selling the trading currency for the base currency) is deliberately not added: its required side is not inferred by symmetry from this one, and adding it requires its own explicit owner-approved rule. `calculate_fx_conversion_policy_id` excludes `conversion_direction` from a V1 instance's identity content before hashing (mirroring `calculate_simulation_run_id`'s V1→V2 pattern for `SimulationRunManifest`), so every already-accepted V1 conversion-policy identity is unaffected — proven by a literal hash, independently computed with the pre-V2 implementation and pinned in a regression test, that still matches after this change.

**Conversion-selection executable boundary — closing the V1-bypass gap (owner-authorized fix, Codex-confirmed finding, 2026-09-19):** the assumption recorded immediately above this paragraph in the original `fx-conversion-policy-v2` entry — that `select_eligible_fx_observation_for_conversion` required no modification because a V2 policy's `quote_convention` is guaranteed correct by construction — was incomplete: the function itself still accepted *any* `FxConversionPolicyConfiguration`, including a `fx-conversion-policy-v1` instance, and selected an observation matching that V1 policy's declared (unenforced) `quote_convention`. Codex's review confirmed this concretely: a hand-constructed `fx-conversion-policy-v1` EUR/USD policy with `quote_convention = ASK` was still accepted by the public selection function and would select a matching ASK observation, silently bypassing the V2 BID rule recorded above. The public function itself, not just the policy type, is now the enforced executable boundary: `select_eligible_fx_observation_for_conversion` requires `policy.schema_version == "fx-conversion-policy-v2"` and `policy.conversion_direction is FxConversionDirection.SELL_BASE_FOR_TRADING`, checked before any observation is examined, and raises a new `FxConversionPolicyUnsupportedError` (a `ValueError` subclass) immediately otherwise — including for a V1 policy whose `quote_convention` happens to already equal `BID`, since V1 carries no structural guarantee and remains independently mutable. This is a raised caller/configuration error, never a returned `FxConversionQuoteUnavailable`, so an unsupported policy can never be mistaken for legitimately missing or stale FX data — the same typed-evidence-vs-raised-invariant distinction already established by `order_resolution.py`'s `OrderResolutionInvariantError`. No established caller depended on V1 compatibility with this function (confirmed by inspecting all call sites before the change: none existed outside `fx.py` and its own test module), so no separate V2-only wrapper was needed and the existing public function was tightened directly. The historical V1 contract itself, `calculate_fx_conversion_policy_id`'s identity algorithm, the pinned V1 identity fixture, and the generic causal-only `select_eligible_fx_observation` are all unchanged by this fix; only the conversion-specific selection function's acceptance criteria tightened. A regression test reproduces Codex's exact V1 EUR/USD ASK scenario and asserts it is now rejected via `FxConversionPolicyUnsupportedError`, alongside tests proving V2 still selects BID and still fails closed (`FxConversionQuoteUnavailable`) when only a non-BID observation is available.

This milestone's steps implement these contracts, the source-checksum helper, the distinct conversion/valuation policy types, and pure quote-side-aware observation selection (`select_eligible_fx_observation_for_conversion`/`_for_valuation`), building on the already-accepted causal-only selection (`select_eligible_fx_observation`, left unmodified). None of this moves capital, builds balanced ledger legs, binds into `SimulationRunManifest` (no V3 schema version yet), or posts anything. `base_currency`/`trading_currency` on a future V3 manifest, and the exact cancellation-at-a-bar's-exact-opening-time behavior for the existing Phase 6.1 order resolver, remain recorded as approved design intent for later steps of this milestone, not implemented here.

**Calculated conversion amount — `calculate_fx_conversion` (owner-authorized, implementation candidate, 2026-09-19):** a pure, deterministic calculation of the trading-currency amount produced by selling a positive `base_amount` of the base currency, for `SELL_BASE_FOR_TRADING` only. This is a **calculated amount, not an executed or posted conversion** — the distinction this paragraph exists to record: `FxConversionCalculation`, the returned result type, moves no capital, mutates no balance, builds no balanced ledger leg, places no broker order, and binds into no run manifest; its own docstring and a dedicated test assert none of its fields name a balance, capital, fill, order, posting or ledger concept. `calculate_fx_conversion` takes the raw causally-released observation prefix, the policy, the amount, an explicit `trading_currency_minor_unit_digits`, and the evaluation time — it never accepts an already-selected `FxObservationReference` from a caller. It selects the observation itself by delegating entirely to `select_eligible_fx_observation_for_conversion`, so the V2/`SELL_BASE_FOR_TRADING`/BID/causal-eligibility boundary recorded in the two paragraphs above cannot be bypassed: a `fx-conversion-policy-v1` policy or any non-BID observation is rejected or returned as typed unavailable evidence exactly as that selector already does, before any arithmetic runs. The exact amount, `base_amount * rate`, is computed once at this project's existing 34-digit `ROUND_HALF_EVEN` Decimal precision with no intermediate rounding, and is kept as `exact_trading_amount`, distinct from `rounded_trading_amount` — a single, final quantization to `trading_currency_minor_unit_digits` decimal places, using `ROUND_HALF_EVEN_V1`. `trading_currency_minor_unit_digits` has no default and is never assumed to be 2, closing item 2 of the five remaining FX design decisions above for this one calculation; a new raised `FxConversionInputError` fails closed on a float, non-Decimal, non-finite (including NaN/Infinity), zero or negative `base_amount`, a negative minor-unit-digit count, or an unsupported rounding policy — the same raised-caller-error-vs-typed-evidence split `FxConversionPolicyUnsupportedError` already established. `FxConversionCalculation` is not itself content-identified: it is a plain, auditable return value referencing the existing `fx_conversion_policy_id`/`fx_observation_id` identities rather than minting a new identity domain, so no domain-identity or schema change was needed to add it. No conversion fee, commission, spread or slippage is applied; no reporting-only valuation calculation is implemented; the reverse conversion direction is not added.

**Numerical-safety corrections to `calculate_fx_conversion` (owner-authorized, focused inspection, 2026-09-19):** two gaps were found by inspection before this candidate was committed, both fixed within the same not-yet-committed slice, neither changing any approved contract or the shared precision/rounding policy. First, Decimal arithmetic rounds *every* operation to fit the ambient context's precision, not only an explicit `.quantize()` call: a plain `Context(prec=34, rounding=ROUND_HALF_EVEN)` multiplication can silently discard significant digits whenever the true product of `base_amount * rate` needs more than 34 of them, with no error raised — which would have made a value labeled `exact_trading_amount` not actually exact, in violation of the no-intermediate-monetary-rounding rule recorded above. Because `FxConversionCalculation`'s own result validator originally recomputed that same product through an identical, non-trapping `Context(prec=34, ...)`, it could not have caught this either — it only proved self-consistency with itself, never mathematical exactness. The fix, `_exact_multiply`, performs the multiplication inside a `Context(prec=34, rounding=ROUND_HALF_EVEN, traps=[Inexact, ...])`: if the true product needs more than 34 significant digits, Python's `Inexact` signal fires and is converted into a raised `FxConversionInputError` instead of a silently rounded result. Both `calculate_fx_conversion` and `FxConversionCalculation.validate_calculation` now call this same helper, so the validator can no longer reproduce the precision loss independently and wrongly accept it; a regression test proves this directly by hand-constructing an `FxConversionCalculation` with a precision-losing `exact_trading_amount` and confirming it is rejected. The shared 34-digit `ROUND_HALF_EVEN` precision/rounding policy itself is unchanged everywhere else in the codebase. Second, `trading_currency_minor_unit_digits` was validated only for `< 0`; because `bool` is a Python `int` subclass (and Pydantic's own default lax `int` field validation accepts it too), passing `True`/`False` was silently treated as a precision of 1/0 rather than rejected, and passing a float, string or `None` raised an undocumented, uncontrolled `TypeError` instead of the documented `FxConversionInputError`. `_validate_minor_unit_digits` now explicitly rejects `bool` and every other non-`int` type, on both `calculate_fx_conversion`'s parameter and `FxConversionCalculation`'s own field; a negative value and an excessively large value (already correctly routed through `FxConversionInputError` via the existing `quantize` `InvalidOperation` catch) remain rejected, and no production currency-specific precision value is invented or silently clamped.

## Rationale

Keeping FX cost out of `TransactionCostConfiguration` avoids retroactively changing an already-accepted, identity-stable contract and matches the architecture document's instruction to track commission, spread, slippage, exchange/regulatory and FX costs separately. A sourcing/audit envelope around the cost profile turns "no run may start until sourced and versioned" from a documentation statement into an enforced, testable fail-closed gate. Modeling FX evidence on the existing causal `MarketEventReference` shape reuses a boundary the project has already built, reviewed and tested rather than inventing a parallel one. Leaving quote convention, staleness threshold and rounding as explicit versioned fields with no default prevents an implicit, unreviewed production choice from being smuggled into configuration, consistent with `docs/PROJECT_RULES.md`'s prohibition on silently changing cost or execution assumptions.

## Consequences

Three new domain identities (`FxObservationId`, `FxConversionPolicyId`, `FxValuationPolicyId`) and one new sourcing identity (`CostProfileRegistrationId`) are added additively to `ai_trading_scanner.domain`; no existing identity type or value changes. No existing `TransactionCostConfiguration`, `calculate_cost_model_id`, `calculate_fill_costs`, `select_eligible_fx_observation`, `FxObservationUnavailable`, `SimulationRunManifest`, or Phase 1–6.1 content identity changes, and every already-accepted V1 `FxConversionPolicyConfiguration` identity is unaffected by the additive `fx-conversion-policy-v2` support (`FxConversionDirection`), proven by a pinned literal hash. The project can now calculate, but still cannot execute, post, or produce a fill's cost with, an FX conversion: pure causal and quote-side-aware observation selection exist, a `V2` conversion policy can no longer be registered with the wrong quote side for the one owner-approved direction, `select_eligible_fx_observation_for_conversion` itself rejects any policy that is not exactly `fx-conversion-policy-v2`/`SELL_BASE_FOR_TRADING` (raising `FxConversionPolicyUnsupportedError`), and `calculate_fx_conversion` now produces a pure, non-posting `FxConversionCalculation` (exact and rounded trading-currency amounts, referencing the selected policy and observation) for `SELL_BASE_FOR_TRADING` only — but balanced-leg capital posting, actual conversion execution, conversion fees/spread/slippage, and manifest V3 binding do not exist, each requiring its own review. Any run manifest that eventually claims `simulation-run-manifest-v3` will require `base_currency`, `trading_currency` and a bound `FxConversionPolicyConfiguration`; this ADR records that intent without implementing it. Real IBKR commission values and a real FX provider/rate/freshness threshold remain unselected and continue to block any non-synthetic run.

## Alternatives considered

Extending `TransactionCostConfiguration` with FX fields (rejected: would change an accepted identity-stable contract for a concern the architecture document treats as separate); hard-coding a placeholder FX rate or staleness threshold "for now" (rejected: PROJECT_RULES.md forbids inventing cost/FX assumptions, and a placeholder risks being mistaken for a sourced value); picking one quote convention (e.g. mid) as an implicit default (rejected: makes an unreviewed production choice invisible in configuration); implementing the full causal resolver and posting in this same step (rejected: exceeds the explicitly authorized bounded scope and would combine evidence contracts with execution behavior in one unreviewed increment).

## Conditions for revisiting

Revisit through a new version once a real FX provider, methodology and staleness threshold are sourced and owner-approved; once `SIMULATED_IBKR_US_TIERED`'s real commission schedule is sourced; when the causal FX resolver, balanced-leg calculation and manifest V3 binding are implemented (each its own bounded, reviewed step per the Phase 6 milestone table); and when the Phase 6.1 cancellation-at-bar-open behavior is either confirmed as a permanent regression test or deliberately changed through a separate explicit decision.
